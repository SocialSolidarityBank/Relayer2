# ASTRA 온보딩 설계 검토 (2026-09-17, gpt-6-astra)

> 가입·기관 워크스페이스·마법사 재설계의 근거. 결정은 SPEC §24, 용어는 GLOSSARY §15-2.

## 结论：拆开“账号注册”和“机构初始化”，但不引入“无所属账号”

**建议采用“邀请制的单机构部署”，而不是照搬 Slack 的多工作区账号模型。** 产品所有者希望调整的**页面顺序**可以实现，但“在统一网站注册后创建机构域名”的能力，超出了当前架构。

> **推荐主流程**
>
> 新部署：`注册首位管理员账号 → 创建机构工作区〔引导第 0 步〕→ 完成机构引导 → 查看咨询日程`
>
> 已有机构：`登录 → 查看咨询日程`，或 `管理员邀请链接 → 注册并加入 → 查看咨询日程`
>
> 未受邀访客：`点击注册 → 显示“该机构仅支持邀请加入” → 登录／联系机构管理员`

# 1. 권고 요약

**계정 가입과 기관 설정은 화면·API에서 분리하되, 공개 가입은 새 배포의 첫 관리자에게만 허용하세요.**

| 결정 항목 | 권고 |
|---|---|
| `가입하기` 노출 | 랜딩·로그인에 항상 표시할 수 있음. **노출과 가입 허용은 별개** |
| 첫 가입 | 계정 정보만 입력 → 첫 관리자 생성·자동 로그인 |
| 기관 만들기 | 관리자 마법사의 **0단계**. 기관 이름 설정, 배포 주소 확인 |
| 기존 기관의 낯선 방문자 | 계정 생성하지 않음. 초대 전용 안내와 로그인 제공 |
| 소속 없는 계정 | 도입하지 않음. 현재 단일 테넌트에서 유의미한 역할이 없음 |
| 워크스페이스 정보 화면 | `#/workspace`: **완료 후 상시 접근 가능한 기관 요약 화면**. 매번 거치는 중간 화면은 아님 |
| 로그인 후 기본 목적지 | `#/schedule`, 화면명은 **상담 일정 보기** |
| 마법사 완료 후 | 기본적으로 `#/schedule`. 기존 `#/participants/new` 이동 제거 |
| slug | 기본적으로 **배포자가 지정하고 관리자는 확인**. DNS 생성 기능처럼 표현하지 않음 |
| 용어 충돌 | GLOSSARY 변경을 승인받아 `워크스페이스`를 **기관 환경의 생성·요약 화면에만 제한적으로 허용** |

### 구현 전에 합의할 아키텍처 경계

이미 이 SPA에 접속했다면 **배포에 접근할 주소는 이미 존재합니다.** 기관 이름이 아직 없거나 `onboarded_at`이 비어 있어도 접속 주소가 없는 것은 아닙니다.

따라서 오너의 요구는 다음처럼 구분해야 합니다.

- **현재 구조에서 가능:** 기관 정보를 계정 가입 뒤에 물어보기.
- **현재 구조에서 불가능:** 공용 `relayer.kr`에서 누구나 계정을 만든 뒤, 기관별 프로세스·DB·DNS를 자동 생성하기.
- 후자까지 원한다면 별도의 **계정·기관 디렉터리와 배포 프로비저닝 계층**이 필요합니다. 가입 폼을 나누는 수준의 변경이 아닙니다.

이하의 `/`, `#/signup` 등은 **각 기관 배포 내부 주소**를 뜻합니다. 별도 공용 마케팅 랜딩의 `가입하기`는 기관 배포 준비나 초대 안내로 연결해야 하며, 임의의 기관 DB에 계정을 만들면 안 됩니다.

# 2. 레퍼런스 적용 원칙

아래는 공식 도움말에 공개된 일반적인 제품 모델을 기준으로 한 비교입니다. 최신 화면의 정확한 버튼 문구·순서는 실시간 확인하지 않았으므로 그대로 인용하지 않습니다.

| 레퍼런스 | 참고할 패턴 | 릴레이어에 그대로 가져오면 안 되는 부분 |
|---|---|---|
| Slack — [도움말](https://slack.com/help)의 워크스페이스 생성·찾기·가입 안내 | 계정 확인과 워크스페이스 진입을 구분하고, 초대로 참여하는 흐름 | 워크스페이스 찾기·여러 워크스페이스 전환은 중앙 계정·소속 탐색 기반이 필요함 |
| Notion — [도움말](https://www.notion.com/help)의 워크스페이스 생성·전환 안내 | 계정과 작업 공간을 개념적으로 분리 | 여러 워크스페이스 중 선택하는 모델은 현 구조와 다름 |
| Linear — [문서](https://linear.app/docs)의 워크스페이스·멤버 관리 | 초대로 팀에 합류하고, 가입 뒤 실제 업무 화면으로 진입 | 이메일 도메인 기반 합류 등 다른 가입 정책은 채택하지 않음 |
| Google Workspace — [관리자 도움말](https://support.google.com/a/)의 초기 설정·도메인 관련 안내 | 관리자 설정과 일반 사용자 이용을 분리, 주소·도메인은 기술적 설정으로 취급 | 릴레이어에 도메인 확인·DNS 자동화가 이미 있다고 가정하면 안 됨 |
| Figma — [도움말](https://help.figma.com/)의 팀·조직·초대 관련 안내 | 가입 경로 자체와 리소스 접근 권한을 별도로 판단 | 전역 계정을 만들 수 있다는 점이 기관 데이터 접근 허용을 뜻하지 않음 |
| 국내 기관용 SaaS | **추정:** 계약·기관 개설 후 관리자가 이용자를 초대하는 방식이 이 제품과 잘 맞음 | 확인한 특정 제품·문서 없이 이를 국내 제품의 공통 사실로 단정하지 않음 |

**핵심은 레퍼런스의 화면이 아니라 원칙을 차용하는 것입니다.**  
“계정과 기관 설정의 분리”는 채택하되, “중앙 계정으로 여러 기관 탐색”은 채택하지 않습니다.

# 3. 권고 흐름 한 장: 상태 → 화면 → 다음

`기관 설정됨`과 `온보딩 완료`를 구분합니다.

- **기관 설정됨:** 기관 이름 등 기관의 식별 정보가 설정된 상태.
- **온보딩 완료:** `organization.onboarded_at != null`.
- `organization` 행이 존재한다는 사실만으로 기관 설정 완료로 보지 않습니다.

| 상태 | 보여줄 화면 | 허용 행동 | 다음 |
|---|---|---|---|
| 로그아웃, 루트 방문 | 랜딩 | `로그인하기`, `가입하기` | 로그인 또는 가입 상태 판정 |
| 로그아웃, 새 배포·첫 가입 가능 | 계정 가입 | 아이디·비밀번호·이름 입력 | 첫 관리자 생성·자동 로그인 → 마법사 |
| 로그아웃, 첫 가입 종료 | 초대 전용 안내 | 로그인, 관리자에게 초대 요청 안내 | 로그인 또는 받은 초대 링크로 진입 |
| 첫 관리자, 기관 미설정 | 마법사 0단계 | 기관 이름 설정·기관 주소 확인 | 기관 정보 단계 |
| 첫 관리자, 기관 정보가 이미 설정됨 | 기존 기관명 안내 + 마법사 | 해당 기관 초기 설정 계속 | 미완료 단계 |
| 로그인한 관리자, 기관 미설정 | 마법사 0단계 | 기관 만들기 | 기관 정보 단계 |
| 로그인한 관리자, 마법사 미완료 | 관리자 마법사 | 정보 → 사업 → 초대 → API 연결 → 완료 | 기본 `#/schedule` |
| 로그인한 사용자, 온보딩 완료 | 상담 일정 보기 | 업무 수행, 기관 정보 열기 | 각 업무 화면 |
| 초대받은 실무자, 기관 준비 완료 | 초대 확인 → 가입·합류 | 초대에 지정된 권한으로 가입 | 기본 `#/schedule` |
| 초대받은 실무자, 기관 준비 중 | 가입·합류 후 준비 중 안내 | 로그아웃, 준비 상태 다시 확인 | 기관 완료 후 `#/schedule` |
| 세션 끊김, 깊은 주소 접근 | 로그인 | 재인증 | 권한·준비 상태 확인 후 원래 주소 복귀 |

### 우선순위

인증 후 라우팅 판정은 다음 순서로 통일합니다.

1. 계정 활성 상태·권한 확인.
2. 초대 수락처럼 진입 맥락에 필요한 작업 처리.
3. 관리자이고 기관 미설정 또는 온보딩 미완료 → 마법사.
4. 실무자이고 기관 준비 중 → 준비 중 안내.
5. 유효하고 접근 가능한 `returnTo`가 있으면 복귀.
6. 그 외 → `#/schedule`.

**기관 설정 마법사 때문에 보류한 `returnTo`는 완료까지 유지합니다.**  
단, 로그아웃하거나 다른 계정으로 전환할 때는 이전 계정의 복귀 정보를 그대로 재사용하지 않습니다.

# 4. 라우트 표

`?step=workspace`는 **해시 안의 쿼리**입니다. 현재 라우터가 지원하지 않으면 동일한 상태를 마법사 내부에서 관리해도 됩니다.

| 주소 | 누가 | 언제·화면 | 다음 |
|---|---|---|---|
| `/`, `#/` | 로그아웃 사용자 | 루트에서만 랜딩 | `#/login`, `#/signup` |
| `/`, `#/` | 로그인 사용자 | 도착 상태 판정 | 마법사 / 준비 중 / 일정 |
| `#/login` | 로그아웃 사용자 | 로그인 폼. `가입하기` 보조 링크 | `returnTo` 또는 상태별 목적지 |
| `#/signup` | 로그아웃, 첫 가입 가능 | **계정만** 가입 | 자동 로그인 → `#/onboarding` |
| `#/signup` | 로그아웃, 첫 가입 불가 | 초대 전용 안내. 가입 폼 없음 | 로그인 / 초대 링크 안내 |
| `#/signup` | 로그인, 관리자·미완료 | 중복 가입시키지 않음 | `#/onboarding` |
| `#/signup` | 로그인, 준비 완료 | 이미 가입된 기관 안내 | `#/workspace` |
| `#/signup` | 로그인한 실무자, 준비 중 | 중복 가입시키지 않음 | `#/setup-pending` |
| `#/invite/:token` | 초대받은 사용자 | 초대 유효성·대상 기관 확인 → 가입 또는 합류 | 일정 / 준비 중 |
| `#/onboarding?step=workspace` | 관리자 | 기관 미설정일 때 0단계 | 기관 정보 단계 |
| `#/onboarding` | 관리자 | 나머지 초기 설정. 재접속 시 미완료 단계 | 완료 → 일정 또는 보류한 목적지 |
| `#/workspace` | 로그인한 멤버 | 온보딩 완료 후 기관 요약 | `#/schedule`, 관리자에게 설정 링크 |
| `#/workspace` | 관리자·미완료 | 요약 화면 우회 불가 | `#/onboarding` |
| `#/setup-pending` | 실무자 | 관리자가 기관 준비 중 | 완료 확인 후 일정 |
| `#/schedule` | 준비 완료된 멤버 | 기본 홈, 상담 일정 보기 | 업무 화면 |
| `#/cases/12/info` 등 보호 주소 | 권한 있는 멤버 | 실제 업무 화면 | 미로그인 시 목적지 보존 후 로그인 |

`participant`는 로그인 사용자가 아니므로 이 가입·멤버 라우트의 대상이 아닙니다.

# 5. A~G: 결론·근거·대안

## A. 기존 기관에서 낯선 사람이 `가입하기`를 누르면?

### 결론

**가입하기는 보여주되 계정 생성은 막고, 초대 전용 안내를 보여주세요.**

표시 내용:

- 공개 표시가 허용된 기관 이름.
- “이 기관은 초대 링크로만 가입할 수 있어요.”
- “기관 관리자에게 초대 링크를 요청해 주세요.”
- `로그인하기`.
- “초대 링크를 받았다면 해당 링크를 열어 주세요.”

사업자등록번호·주소·전화번호·사용자 목록까지 공개할 필요는 없습니다.

### 근거

Slack의 워크스페이스 찾기는 중앙에서 계정과 소속을 연결하는 모델에 적합합니다. Figma도 계정 보유와 특정 리소스 접근 권한을 구분합니다.

하지만 릴레이어는 **이 배포 자체가 한 기관**입니다. 여기에 낯선 사람의 계정을 저장하면 “다른 기관을 찾는 계정”이 아니라 “이 기관 DB에 존재하지만 권한이 없는 계정”이 됩니다.

현재 역할만으로 이를 안전하게 표현하기도 어렵습니다. `worker`로 저장하면 실무자 권한으로 오인될 위험이 있고, 별도 대기 상태·권한 정책·삭제 정책이 필요합니다.

### 대안 하나

별도의 중앙 계정 서비스를 만들고, 기관에 속하지 않은 계정은 **중앙 서비스에만** 저장합니다. 초대 수락 시 해당 기관으로 연결합니다.

이는 향후 다기관 제품 전환안이지, 현재 브랜치의 최소 변경안은 아닙니다.

## B. 기관 만들기와 마법사의 관계는?

### 결론

**기관 만들기는 마법사 0단계로 통합하세요.**

```text
계정 가입
  → 0. 기관 이름 설정·주소 확인
  → 1. 기관 정보
  → 2. 사업 1개 이상
  → 3. 실무자 초대〔건너뛰기 가능〕
  → 4. OpenAI API 연결
  → 5. 완료
```

- 계정 가입 폼에서 기관 이름·slug를 제거합니다.
- 기관이 이미 설정되어 있으면 0단계를 건너뜁니다.
- 기관을 만든 직후 정보 화면이나 대시보드로 보내지 않습니다.
- `onboarded_at`이 비어 있으면 관리자는 계속 마법사에 머뭅니다.
- 초대 단계는 “메일 보내기”가 아니라 **초대 링크 만들기·복사하기**입니다.

### 근거

Notion·Slack의 계정/공간 구분은 화면을 나누는 근거가 됩니다. Google Workspace의 관리자 초기 설정 모델은 “기관이 존재함”과 “업무 이용 준비가 끝남”을 구분하는 근거가 됩니다.

### 대안 하나

`#/workspace/new`를 별도 화면으로 두고 저장 후 `#/onboarding`으로 이동합니다.

단, 생성 화면도 초기 설정 게이트의 일부로 취급해야 합니다. 별도 화면을 만들더라도 **기관 생성 직후 일정으로 이동하는 예외는 두지 않습니다.**

## C. `#/workspace`는 어떤 화면인가? 로그인한 사람이 가입하기를 열면?

### 결론

**기관 요약 화면으로 상시 제공하되, 일상적인 로그인 과정에서는 생략하세요.**

권장 구성:

| 내용 | 표시 범위 |
|---|---|
| 기관 이름 | 로그인한 멤버 |
| 현재 배포의 접속 주소 | 설정된 신뢰 가능한 주소가 있을 때 |
| 내 이름·역할 | 본인 |
| 기관 준비 완료 상태 | 로그인한 멤버 |
| `상담 일정으로 이동하기` | 준비 완료된 멤버 |
| `기관 설정 보기` | 관리자 |
| API 키 | 표시하지 않음 |
| 사업자등록번호·연락처 상세 | 필요하다면 관리자 설정에서 제공 |

사이드바의 설정 묶음에서 `기관 정보`로 접근하도록 합니다. 별도의 “워크스페이스 전환기”는 만들지 않습니다.

로그인한 사용자가 `#/signup`을 열면:

- 관리자·미완료 → 마법사.
- 준비 완료 → 기관 요약.
- 실무자·준비 중 → 준비 중 안내.

### 근거

Slack·Notion의 공간 선택 화면은 여러 공간을 선택할 때 가치가 있습니다. 한 기관만 있는 제품에서 매번 기관 확인 화면을 거치면 클릭만 늘어납니다.

오너의 “있으면 정보가 뜨고 링크로 넘어간다”는 요구는 **가입 진입 경로와 기관 정보 화면에서 충족**하고, 평소 로그인은 업무 홈으로 바로 보내는 것이 적절합니다.

### 대안 하나

기관 요약을 가입·초대 수락 직후 한 번만 보여주는 인터스티셜로 사용합니다. 이후에는 설정에만 제공합니다.

다만 “한 번 봤음” 상태가 추가되고 복귀 동선이 복잡해지므로, 상시 화면을 재사용하는 안보다 우선순위가 낮습니다.

## D. 랜딩과 세션 만료 후 깊은 주소 복귀는?

### 결론

**랜딩은 루트에만 표시하고, 보호 주소 방문은 랜딩을 거치지 않고 로그인으로 연결하세요.**

예:

```text
/#/cases/12/info
  → 인증 실패
  → returnTo에 "#/cases/12/info" 저장
  → /#/login
  → 로그인 성공
  → 권한 확인
  → /#/cases/12/info
```

구현 규칙:

- 최초 앱 부팅에서 현재 해시를 먼저 읽고 인증을 확인합니다.
- 인증 실패 시 현재 보호 주소를 `sessionStorage` 등에 저장합니다.
- 해시 경로의 쿼리까지 보존합니다.
- `returnTo`는 내부 라우트만 허용합니다. 임의 외부 URL은 거부합니다.
- `#/login`, `#/signup` 등을 복귀 대상으로 저장해 순환시키지 않습니다.
- API `401`은 로그인, `403`은 권한 없음으로 구분합니다.
- 대상 상담이 삭제됐거나 접근 권한이 없어졌다면 안내 후 일정으로 이동합니다.
- 경로 복귀는 보장하되 **작성 중이던 내용의 복구까지 보장하는 것은 아닙니다.**

### 근거

Slack·Figma 같은 협업 도구에서 링크로 특정 리소스에 들어가는 사용 맥락은 중요합니다. 이를 보존하는 것은 SPA의 인증 후 복귀 설계에 해당하며, 특정 제품의 내부 저장 방식까지 따라야 한다는 뜻은 아닙니다.

### 대안 하나

주소를 바꾸지 않고 현재 보호 화면 위에 로그인 화면을 표시합니다. 성공하면 같은 주소를 다시 렌더링합니다.

주소 보존은 간단하지만, 인증 전 민감한 내용이 잠깐 노출되지 않도록 보호 화면 자체를 렌더링하지 않아야 합니다.

## E. 단일 테넌트에서 slug는 누가 정하고 어떻게 검증하나?

### 결론

**slug는 계정 정보가 아니라 배포 식별 정보입니다. 배포자 지정·관리자 읽기 전용을 기본값으로 권고합니다.**

| 항목 | 권고 |
|---|---|
| 기관 이름 | 관리자가 기관 만들기에서 입력·확인 |
| slug | 배포자가 지정. 초기 설정 화면에서는 읽기 전용 확인 |
| 실제 접속 주소 | 배포 설정에 저장된 신뢰 가능한 URL 표시 |
| slug 변경 | 일반 설정 변경으로 취급하지 않음. DNS·프록시 운영 절차와 연계 |
| 기존 기관 이름이 있는 DB | 기관을 다시 만들지 않음. 마이그레이션 시 기존 설정으로 인정 |
| 기존 `onboarded_at = null` | 기관명 유무와 무관하게 나머지 마법사 진행 |
| 기존 이름만 있고 slug 누락 | 기관이 없다고 판단하지 않음. 배포 설정 문제로 별도 처리 |

검증은 두 층으로 구분합니다.

1. **로컬 검증:** 소문자 영문·숫자·하이픈, 길이, 시작·끝 하이픈 금지, 예약어 등.
2. **배포 검증:** 전체 서비스에서의 중복, DNS·프록시 연결 여부.

DB 하나만 보는 API는 전체 배포의 slug 중복을 확인할 수 없습니다. 따라서 로컬 검증만 하고 “사용 가능한 주소예요”라고 표시하면 안 됩니다.

또한 `<slug>.relayer.kr`을 문자열로 조합했다고 그 주소가 실제로 열리는 것은 아닙니다. 앱이 Host를 읽지 않는 현재 구조에서는 주소 표시가 필요하면 **배포별 명시 설정**을 사용하세요.

### 근거

Google Workspace의 도메인 설정은 도메인 입력과 실제 연결·확인이 별개라는 비교 근거가 됩니다. Slack의 URL 선택 경험을 가져오려면 그 뒤의 주소 할당 시스템도 필요합니다.

### 대안 하나

관리자가 희망 slug를 입력하게 하되 **주소 신청**으로 처리합니다. 배포자가 연결을 완료할 때까지 “주소 연결 대기 중”으로 표시합니다.

자동 예약·연결 기능 없이 “기관 주소가 만들어졌어요”라고 안내하지 않습니다.

## F. `대시보드`와 `워크스페이스` 용어는 어떻게 정리하나?

### 결론

**대시보드라는 화면명을 새로 만들지 말고, `#/schedule`을 계속 `상담 일정 보기`로 부르세요.**

`워크스페이스`는 다음 조건으로만 허용하는 것을 권고합니다.

1. GLOSSARY §15 변경을 제품 오너와 승인합니다.
2. 의미를 **“한 배포에 있는 기관의 업무 환경 전체”**로 고정합니다.
3. 일정 화면이나 홈을 워크스페이스라고 부르지 않습니다.
4. 기관 생성 제목·CTA와 기관 요약 화면에만 제한적으로 사용합니다.
5. 일상 내비게이션은 기존처럼 `일정 / 당사자 / 설정`을 유지합니다.

| 개념 | 사용자에게 보여줄 용어 |
|---|---|
| 기관 환경 생성 | 기관 워크스페이스 만들기 |
| 기관 환경 요약 | 기관 워크스페이스 또는 기관 정보 |
| 로그인 후 홈 | 상담 일정 보기 |
| 기관 환경으로 이동하는 버튼 | 상담 일정으로 이동하기 |
| 일반 설정 | 기관 설정 |
| 기관 구성원 | 관리자·실무자 |

### 근거

Slack·Notion은 작업 공간과 그 안의 개별 업무 화면을 구분합니다. 이 구분을 차용해야지, 일정 화면을 “워크스페이스”로 다시 부르면 기존 혼동이 반복됩니다.

### 대안 하나

기존 GLOSSARY를 유지하고 `기관 공간 만들기` 또는 `기관 설정 시작하기`를 사용합니다.

다만 오너가 요구한 문구와 달라지므로, 구현자가 조용히 대체하지 말고 **요구 변경 승인 사항**으로 남겨야 합니다.

## G. 서버 계약 최소 변경안

### 결론

**기관 생성 엔드포인트를 새로 만들기보다, `/auth/signup`에서 기관 필드를 제거하고 `PUT /settings/org`를 재사용하세요.**

#### 1) 첫 관리자 가입

```http
POST /auth/signup
```

```json
{
  "username": "worker01",
  "password": "...",
  "name": "김실무"
}
```

- 기관 이름·slug 제거.
- 역할은 서버가 `admin`으로 결정.
- **새 배포이면서 활성 관리자 0명**인 경우에만 허용.
- 가입 가능 확인과 첫 관리자 생성은 하나의 원자적 처리로 수행.
- 첫 관리자 생성 즉시 공개 가입 종료.
- 이미 닫힌 경우 `SIGNUP_CLOSED` 같은 안정적인 오류 코드 반환.
- 초대 가입은 기존 초대 수락 API에서 처리. 공개 가입 API의 우회로로 사용하지 않음.

#### 2) 로그인 전 상태

로그인 전 화면은 `/me`로 판정할 수 없으므로 기존 공개 부트스트랩 응답에 다음 필드를 추가하거나, 작은 공개 상태 API를 둡니다.

```json
{
  "signup_available": false,
  "organization_display_name": "릴레이복지관"
}
```

이 값은 화면 표시용입니다. 서버는 실제 가입 요청 시 다시 검사합니다.

#### 3) `/me`

기관 미설정:

```json
{
  "user": {
    "id": 1,
    "name": "김실무",
    "role": "admin"
  },
  "workspace": null,
  "onboarded": false
}
```

기관 설정됨:

```json
{
  "user": {
    "id": 1,
    "name": "김실무",
    "role": "admin"
  },
  "workspace": {
    "name": "릴레이복지관",
    "slug": "relay-welfare",
    "url": "https://relay-welfare.relayer.kr"
  },
  "onboarded": false
}
```

- `workspace`는 **기존 단일 `organization` 행의 응답용 표현**입니다.
- `organizations` 테이블·`org_id`는 추가하지 않습니다.
- `url`은 명시적으로 설정된 실제 배포 주소만 반환하며, 없다면 `null` 또는 생략합니다.
- `onboarded`는 `onboarded_at`에서 계산합니다.
- 선택적으로 `onboarding_step`을 제공할 수 있지만, 서버에서 실제 완료 조건을 계산해야 합니다.
- 평문 API 키와 `enc_openai_key`는 반환하지 않습니다.

#### 4) 기관 만들기

```http
PUT /settings/org
```

0단계에서는 기관 이름 등 해당 단계 필드를 저장합니다. 기존 엔드포인트가 전체 필드를 요구한다면, **초기 설정 중 단계별 저장을 허용하도록 계약을 명시적으로 조정**합니다. 빈 값으로 기존 정보를 덮어쓰면 안 됩니다.

- 관리자 전용.
- 단일 행 `id=1`을 초기화하거나 갱신.
- 관리형 slug는 클라이언트 수정 거부.
- 중복 제출해도 기관이 추가로 생성되지 않음.
- 기존 기관의 값이 있으면 클라이언트에 최신 상태를 돌려주고 이어서 설정.

`POST /settings/workspace`는 새 리소스를 추가하는 인상을 주므로 최소 변경안에는 불필요합니다.

#### 5) 게이트는 분리

| 행위 | 서버 조건 |
|---|---|
| 공개 첫 가입 | 새 배포의 부트스트랩이 열려 있음 **AND** 활성 관리자 0명 |
| 기관 최초 설정 | 인증된 관리자 **AND** 기관 미설정 |
| 기관 설정 수정 | 인증된 관리자 |
| 초대 생성 | 인증된 관리자. 온보딩 중에도 가능 |
| 초대 수락 | 유효한 7일 초대, 미폐기·미사용 등 초대 정책 충족 |
| 온보딩 완료 처리 | 필수 기관 정보·사업 1개 이상·API 연결 단계의 요구조건 충족 |
| 업무 데이터 이용 | 역할 권한 충족. 본 권고에서는 기관 준비 완료도 요구 |

특히 다음은 금지합니다.

- `workspace == null`이라는 이유로 낯선 사람의 공개 가입 허용.
- 첫 관리자 생성 뒤에도 기관 미설정이라는 이유로 두 번째 공개 가입 허용.
- 관리자 수가 운영 사고로 0이 됐다는 이유로 공개 가입 재개.

**“새 배포”는 관리자 수만으로 완전히 표현되지 않습니다.** 기존 스키마로 최초 가입 완료 이력을 확실히 판정할 수 없다면, `bootstrap_closed_at` 같은 영구적인 마감 표식 하나를 추가하는 것이 안전합니다. `onboarded_at`은 첫 가입 후 한동안 비어 있으므로 대체할 수 없습니다.

또한 클라이언트 리다이렉트는 UX 제어일 뿐입니다. 관리자 설정·초대·업무 API의 권한 검사는 서버에서도 독립적으로 수행해야 합니다.

### 근거

Google Workspace의 관리자/사용자 분리와 Linear의 멤버 초대 모델은 역할별 진입을 나누는 근거입니다. 다만 위 API 형태와 단일 행 갱신 방식은 레퍼런스 복제가 아니라 **릴레이어의 현재 데이터 모델에 맞춘 설계**입니다.

### 대안 하나

기관 최초 설정을 명령으로 명확히 분리하고 싶다면 `POST /settings/workspace`를 둡니다.

단, 이 API 역시 `organization(id=1)`만 초기화해야 하며, 이미 설정된 경우 충돌 응답을 반환해야 합니다. 멀티테넌트 생성 API처럼 동작하게 만들지 않습니다.

## 최종 결정안

> **“가입하기”는 항상 찾을 수 있게 하되, 가입 권한은 초대와 첫 관리자 예외로 제한합니다. 계정 가입 뒤 기관 만들기를 마법사 0단계로 제공하고, 기존 기관은 재생성하지 않습니다. 기관 정보 화면은 필요할 때 확인하는 요약 화면이며, 평소 업무 진입점은 ‘상담 일정 보기’입니다.**

이렇게 하면 오너가 요구한 **계정과 기관 생성의 분리**를 충족하면서도, 현재의 **단일 배포·단일 기관·초대 전용 보안 모델**을 유지할 수 있습니다.
