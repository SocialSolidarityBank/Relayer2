## 2. 용어가 계속 흔들린 진짜 원인과 처방

잦은 수정의 원인은 개별 단어가 아니라 **이름의 세 층이 한 곳에 없었다는 것**이다.

| 층 | 예 | 바뀌는가 |
|---|---|---|
| 표시명 | `15초 다시보기` | Q 확정으로 바뀐다 |
| 개체명 | 사례 · 회차 · 과제 | 거의 안 바뀐다 |
| 식별자 | `/briefing` · `beneficiaryId` · `module=audit` | **표시명이 바뀌어도 안 바꾼다** |

그리고 **한 개체가 표면마다 다른 라벨을 갖는 것이 정상**이다. 같은 과제가 쓸 때는 `수행할 과제`, 15초 다시보기에서는 `확인할 과제`, 종결에서는 `미완료 과제`다. 이걸 "불일치"로 보고 통일하려 들면 수정이 반복된다.

**제안**: CCC도 이름 정본을 파일 하나로 모은다. 현재는 `CONTEXT.md`(용어집 333줄) + `DESIGN.md`(786줄) + `handoff-decisions`(01~54) + PLANNER 표시명 표에 흩어져 있고, 화면 라벨이 어디를 따라야 하는지가 문서마다 다르다. RELAYER2의 `GLOSSARY.md`를 그대로 틀로 쓰면 된다(표시명 표 / 역할 / 목표 세 층 / 표면별 라벨 / 삭제된 말 / "화면에서 지운다고 자료를 지우는 것이 아니다").

### 3-3. 구조 제안 (삭제가 아니라 이동)

- `gateway.ts` **21,611줄 단일 파일**을 도메인별로 쪼개는 것은 릴레이어가 검증한 경계를 그대로 쓸 수 있다: 카드·목표·회차·브리핑·동의·감사. 릴레이어에서는 같은 기능이 순수 함수 5파일 ~900줄이다.
- `request-handler.ts`의 if-체인 111개 중 파서·직렬화 ~2,400줄은 zod 한 곳으로 증발한다.
- `cards.closed_at` 같은 **상태 중복 소유**를 만들지 말 것. 열림·닫힘은 결과 이벤트에서 파생한다(릴레이어 `api/src/domain/cards.ts` 참조).

## 4. 하지 말 것

- 화면에서 지운 입력을 **자료 파기로 승격하지 않는다.** 위기도·추가 기록·기한·수행 주체는 입력과 표시에서만 사라진다. 저장값·원문·감사 이력은 보존하고, 빈 값을 `안정`이나 `변화 없음`으로 추정해 채우지 않는다.
- **일괄 문자열 치환 금지.** "첫 상담 기록이 있는 사업"처럼 자료를 가리키는 일반 문장, 상담 유형·기록 형식 같은 일반 명사, 과거 결정 문서의 역사 기록은 그대로 둔다. 바꾸는 것은 페이지 제목·메뉴·진입 버튼과 그 제목을 가리키는 안내문이다.
- 표시명이 바뀌었다고 **URL·`module` 값·DB 컬럼·역할 코드·API 경로를 바꾸지 않는다.**
- 문구 고정 테스트를 **새 단어로 다시 고정하지 않는다.** 그 테스트는 지우는 쪽이 맞다.
